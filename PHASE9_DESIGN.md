# Phase 9 design: modules, packages and per-package permissions

Status: 2026-11-15. Steps 9.1 and 9.2 are done; 9.3 is being built; 9.4
follows this document and may refine it, with every change recorded here
and in `HISTORY.md`.

Phase 9 turns Forge from "one script with one policy" into "an app made of
packages, each holding only the permissions it was given". It is the step
that makes Forge different from Node, Deno and Bun, none of which isolate
packages from each other.

## 1. What we learned first (decision D17)

### ShadowRealm (TC39, stage 2.7)

- The proposal's spec draft is still at stage 2.7. **SpiderMonkey ESR 153
  does not ship it** (there is no `builtin/ShadowRealm` in the engine at
  the pinned commit), so Forge cannot build on it.
- Its boundary rule is the strictest one the language community has agreed
  on: only primitives and callables cross; a callable crosses as a new
  "wrapped function" whose arguments and results are wrapped again; any
  other object throws a `TypeError`; an error thrown across the boundary is
  replaced by a fresh `TypeError` in the caller's realm, so the original
  error object never crosses.
- **What Forge takes from it:**
  1. Errors and callables are the classic ways to smuggle authority out of
     a boundary. Forge's wrapper policy treats Forge's own host objects
     (the `fs` functions, `Forge.env`, ...) like ShadowRealm treats every
     object: they never cross into another package.
  2. Package boundaries must not depend on rewriting source text (see
     LavaMoat below). ShadowRealm is engine-enforced; so is Forge.
  3. If ShadowRealm reaches stage 4, Forge exposes it unchanged. A future
     `Forge.isolate()` for running untrusted plug-ins would use the same
     shape (`importValue`, wrapped callables) rather than invent one.

### LavaMoat and SES (the closest prior art to Kavach)

LavaMoat runs each npm package in an SES `Compartment` after `lockdown()`
freezes the shared intrinsics, and gives it only the globals and builtin
modules its `policy.json` lists. Policies are keyed by the package's path
in the dependency tree (`"a>b>c"`), so a same-named package elsewhere
cannot take over its permissions. They are generated by static analysis;
`policy-override.json` adjusts them; entries are an allow-list only
(`"a": true, "a.b": false` does **not** take `a.b` away).

Its published escapes, and what each one means for Forge:

| Escape | Root cause | Forge's rule |
|---|---|---|
| `ses` CVE-2023-39532 (GHSA-9c4h-3f7h-322r): `{...import(x)}` reached the host's dynamic import | A **regular expression** that rejected `import(` in source text missed `...import(` | Never enforce a boundary by scanning or rewriting source. Forge's module load hook sees every `import()` the engine performs, whatever the spelling. |
| `ses` CVE-2025-32792: top-level `let`/`const`/`class` of the page leaked into a Compartment's lexical scope | Compartments shared one global lexical environment | Every Forge compartment has its own global object **and** its own global lexical scope. Nothing is shared lexically. |
| LavaMoat browserify bypass (OtterSec, 2024): a multi-line comment ended the `with(...)` wrapper early | Again a **source transform**, checked before it was applied | Same as the first row. |
| "Scuttling" bypass: `window.open()` gave a fresh, unrestricted realm | A way to create a new realm the policy did not cover | No API reachable from a package creates a realm or global. `eval` and `new Function` are off by default in every package compartment. |

Also taken from LavaMoat: the policy key is the package's **identity in
the graph**, not its name; permissions are allow-lists only; and the
entry (the app) is trusted with the grants on the command line, which cap
everything.

Where Forge differs on purpose: LavaMoat generates permissions from what
the code appears to use and trusts that snapshot. Forge asks the package
author to declare permissions and the app owner to grant them, and the
command line caps the whole program.

## 2. Decisions

| ID | Decision | Why |
|---|---|---|
| D22 | **Forge runs ES modules only.** The file given on the command line is loaded as a module, and so is everything it imports. There is no CommonJS and no classic-script mode for programs (`forge --self-test` still uses scripts internally). | One module system, strict mode everywhere, and module records are what per-package isolation is built on. Deno made the same choice. |
| D23 | **Loading code is not a filesystem permission.** A program may load modules only from its own **module root** (step 9.1) and, from 9.2, from the roots of its declared dependencies. Module paths go through the same path rules, link resolution and handle-based reads as `fs`, and every load is audited as op `import` with permission `module`. `--allow-read` neither adds nor is needed for module roots. | A program must be able to load its own code without being granted read access to it, and a read grant must not turn into a way to load code from somewhere unexpected. |
| D24 | **Caller identity (rule R14, gap G06):** the authority of a native call is the package that owns the realm in which that native function object was created. Every package compartment gets its own copies of Forge's natives, bound to its policy, and those function objects can never be passed into another package. Async work captures the policy when it is queued. | No stack walking and no "scripted caller" lookup, which JIT inlining and promise jobs make unreliable. One rule covers sync calls, promise jobs, timers and signal listeners. |
| D25 | **Compartment layout:** the app gets one compartment; every dependency that holds a permission gets its own; every permission-free dependency shares one "pure" compartment, which has no Forge natives at all and frozen intrinsics. | Isolation where it buys something, without a compartment per tiny package. A pure package cannot reach any authority, because its compartment has none. |
| D26 | **Effective permission = declared ∩ granted ∩ command line.** A dependency declares what it needs in its `forge.json`; the app grants it (9.4: in the app's `forge.json`; Phase 14: approved into `forge.lock`); the command-line grants cap the whole program. | No package can ever exceed what the person running Forge allowed. |

## 3. Modules (step 9.1)

### Entry and module root

- `forge app.js` loads `app.js` as a module. Its **module root** is the
  nearest folder at or above it that contains `forge.json`, or else the
  folder of `app.js`. The search stops before the home folder and before a
  drive or share root; neither can be a module root. If the folder of
  `app.js` would be one of them, the module root is `app.js` alone, so
  nothing else can be imported.
- Every module the program loads must lie inside the module root, before
  and after links are followed, and must not be a protected path.

### Specifiers

Resolved like URLs, as in browsers and Deno, by portable code in
`runtime/ModuleSpecifier.cpp` (unit-tested in the Linux CI job):

| Specifier | 9.1 behaviour |
|---|---|
| `./x.js`, `../lib/y.js` | Resolved against the importing module's `file:` URL. `\` is treated as `/`, as the URL standard does for `file:` URLs. |
| `file:///C:/app/x.js` | Accepted if it is inside the module root. A `file:` URL with a host (a network share) is refused. |
| `/x.js` | Resolves to the drive root, so it is outside the module root and refused. |
| `x`, `@scope/x` (bare) | Refused with code `NotSupported` until packages arrive (9.2). |
| `node:fs` | Always refused (`NotSupported`): Forge has no Node built-ins. |
| `https:`, `http:`, `data:`, `blob:`, `npm:`, `jsr:` | Refused (`NotSupported`). No code is ever loaded from the network. |
| Query (`?v=1`) or fragment (`#x`) | Refused (`InvalidArgument`): they would give one file two module identities. |
| Percent escapes | Decoded; `%00` and escaped separators (`%2F`, `%5C`) are refused. |

There is no extension guessing and no folder `index.js`: the file name must
be written in full, as in browsers.

### Loading

- The engine's module load hook (`JS::SetModuleLoadHook`) is the only way
  code is loaded. Static imports are loaded synchronously while the graph
  is built; dynamic `import()` is deferred to a promise job (as the
  engine's own shell does) so that it is always asynchronous.
- A module's identity is its resolved path (links followed). The same file
  imported twice, by any spelling, is one module.
- Files are read with `kavach/SecureFs` from a `CheckedPath` made for op
  `import`, so module loading gets the same protection as `fs`: path rules,
  link resolution, handle-relative opens and the final-path re-check.
- JSON modules need `with { type: "json" }`; a `.json` file without it, and
  any other `type`, is refused, as the standard requires.
- `import.meta.url` is the module's `file:` URL; `import.meta.main` is true
  for the entry module only; `import.meta.resolve(specifier)` returns the
  URL a specifier would load, without loading it.
- A UTF-8 byte-order mark is skipped. Source must be valid UTF-8.

### Errors

- A failed load rejects or throws an ordinary `Error` with `code`
  (`NotFound`, `PermissionDenied`, `InvalidArgument`, `NotSupported`) and
  a message naming the specifier, the importing module and the reason.
- An exception thrown while the entry module evaluates is reported like an
  uncaught exception (exit code 1). **Known limit:** for a thrown value
  that is not an `Error`, SpiderMonkey's module evaluation keeps only the
  value, so its throw-site stack is not printed (an `Error` prints its own
  stack as before).
- `Forge.exit()` during module evaluation exits with its code, as before.

## 4. Packages and resolution (step 9.2)

**The manifest.** A package is a folder with `forge.json`:

```json
{
  "name": "greet",
  "version": "1.0.0",
  "exports": {
    ".": "./index.js",
    "./extra": { "forge": "./extra-forge.js", "default": "./extra.js" },
    "./features/*": "./features/*.js",
    "./internal": null
  },
  "dependencies": { "@acme/util": "file:../util" },
  "permissions": {}
}
```

- Fields: `name` (required for a dependency; npm-style lower-case names,
  optionally `@scope/`), `version`, `description`, `license`, `author`,
  `exports`, `dependencies`, and `permissions` / `grants` (structure only;
  their meaning comes in 9.4). **Any other field is refused** with a plain
  message, so a misspelt `dependancies` or a `scripts` field Forge would
  never run is not silently ignored. `main`, `module` and `type` get a hint
  to use `exports`.
- Parsed by `runtime/Json.cpp`, a small strict JSON parser (D5: fuzzed C++,
  not the engine): duplicate keys, invalid UTF-8, lone surrogates, comments,
  trailing commas, more than 64 levels or more than 1 MiB are refused,
  because another parser could read such a file differently. The file name
  is one constant (`kManifestName`), so the D1 naming decision stays a
  one-line change.
- forge.json is a protected path (R13): no grant covers it. The loader
  reads it through `kavach::CheckManifest`, which requires the folder to be
  a module root and forge.json to be a plain file there (not a link), and
  audits the read.

**Resolution.**

- A bare specifier resolves only to the package itself (a self-reference
  through its own `exports`) or to a package listed in the importing
  package's `dependencies`: no phantom dependencies. Until the package
  manager exists (Phase 14), a dependency is a local folder,
  `"file:<folder>"`, relative to the declaring package.
- **Only the program's own forge.json may name a folder outside the
  program's folder.** A dependency's `file:` folder must be inside it, so a
  dependency cannot pull code from elsewhere on the disk. The folder must
  hold a forge.json whose `name` matches the dependency's name.
- Subpaths only through `exports`, with Node.js semantics: a string, a
  subpath map (`"."`, `"./x"`, one `*` per key), condition objects, and
  `null` for a private subpath. Forge's conditions are `forge`, `import` and
  `default`, chosen in the order the object lists them (as Node.js does), so
  `{ "default": ..., "forge": ... }` picks `default`. Targets must start
  with `./` and contain no `.`, `..`, `node_modules`, `\`, `%` or `:`
  segment; a pattern substitution that would produce one is refused.
  Arrays of fallbacks are refused for now. A package without `exports`
  exposes nothing.
- **Every module belongs to exactly one package:** the nearest folder with
  forge.json above it. A relative or `file:` import must stay in the
  importing module's package. Reaching into another package by path (the
  program importing `./vendor/greet/internal.js`, or a dependency importing
  `../../src/main.js`) is refused; the only way in is the package's name and
  `exports`. A module already loaded for one package is never handed to
  another by path.
- Each dependency folder becomes a Kavach module root when it is first
  used, with the same refusals as any module root (not a drive root, not
  the home folder, not protected).

## 5. Isolation (step 9.3)

Built in `runtime/Compartments.cpp` (compartments, lockdown, wrapper
policy) and `runtime/Modules.cpp` (facades).

**Layout (D25).** The program runs in the app compartment. A dependency
that holds a permission will get its own compartment in 9.4; until then no
dependency can hold one (grants arrive in 9.4, and D26 intersects with
them), so **every dependency runs in one shared "pure" compartment**. All
compartments are in the program's zone, so calls between them are cheap.
The pure compartment is created on first use, with the same global class
and realm options as the program's.

**What a package's compartment has.** The standard JavaScript globals,
plus `console`, `setTimeout`, `setInterval`, `clearTimeout`,
`clearInterval` and `queueMicrotask`: the WinterTC minimum that holds no
authority. No `fs`, no `Forge`, no `print`. *Refinement:* D25 said "no
Forge natives at all"; these six hold no authority, and without them most
libraries do not run. A timer belongs to the realm that created it: its
callback runs there, and only that realm can cancel it, so a package cannot
clear the program's timers by guessing ids. `console.count` and
`console.time` labels are per realm too.

**Lockdown.** In a dependency compartment every intrinsic is frozen:
everything reachable from the standard globals through prototypes,
property values, getters and setters, plus the hidden intrinsics no
property path reaches (`%ArrayIteratorPrototype%`, the other iterator
prototypes, `%GeneratorFunction%`, `%AsyncFunction%`,
`%AsyncGeneratorFunction%`, the iterator-helper prototypes, Intl segment
prototypes), found by a fixed script run before any package code. The
walk starts from the names of the standard globals, captured before Forge
adds its own, so a Forge object is never taken for an intrinsic. The
compartment's global object, `console` and the timer functions are frozen
too: pure packages share the compartment, so nothing on it may change.

- **The override mistake.** Assigning to a property an object inherits
  from a frozen prototype throws in strict code, which would break
  `this.name = "MyError"`, `Foo.prototype.toString = ...` and
  `Child.prototype.constructor = Child`. As in SES, a few data properties
  become accessors before freezing: the getter returns the original
  value; the setter defines an own property on the object assigned to and
  still refuses the built-in itself. The list: `constructor`, `toString`,
  `toLocaleString` and `valueOf` of `Object.prototype`; `constructor` and
  `toString` of `Function.prototype`; `constructor`, `name`, `message` and
  `toString` of `Error.prototype` and of every native error's prototype.
  The prototypes behind the engine's fast paths (`Array`, `Promise`,
  `RegExp`, the collections) are left alone, as are hot methods.
- **R19, engine state that freezing misses.** The legacy RegExp statics
  (`RegExp.lastMatch`, `RegExp.$1`, `RegExp.input`, ...) are permanent
  accessors in a release build, so they cannot be removed. They are per
  realm: the program and the packages never see each other's matches
  (tested). **Known limit:** pure packages share a realm, so one pure
  package can read the last match of another. `Math.random` shares one
  generator per realm in the same way (no secret is involved). The
  `Symbol.for` registry is shared by every realm, as the language
  requires; symbols carry no authority.
- The program's own compartment is not frozen, so programs that patch
  built-ins keep working. `--frozen-intrinsics` freezes it too (same walk,
  same accessors); the program keeps its natives and `eval`.

**Wrapper policy** (`JS_SetWrapObjectCallbacks`, the pre-wrap callback).
Every object that crosses from one compartment to another passes through
it, whichever way it crosses (argument, return value, property read,
exception, promise result):

1. A global object never crosses (`TypeError`, code `PermissionDenied`).
2. Forge's own objects never cross: every native Forge defines on a
   global (the `fs` functions, `console`'s, `Forge`'s, the timers),
   every object that holds one (`fs`, `console`, `Forge`, `Forge.env`),
   `import.meta.resolve`, and a bound function whose target is one of
   these. Plain data such as `Forge.args` crosses. This is what makes D24
   sound: a package never holds a function whose authority is another's.
3. An intrinsic is **replaced by the receiving compartment's own
   intrinsic of the same identity**. Both compartments' intrinsics are
   walked in the same canonical order (own keys sorted), so the n-th
   intrinsic of one is the n-th of the other; a signature (class name,
   number of own keys, callable) must also match. So a package never holds
   the program's `Object.prototype`, `Function` constructor or `eval`:
   `Object.getPrototypeOf(programObject)` gives the package's own frozen
   `Object.prototype`, and `programObject.constructor.constructor` is the
   package's `Function`, which cannot compile strings. A useful side
   effect: `x instanceof Array`, `Object.getPrototypeOf(x) ===
   Object.prototype` and `err instanceof TypeError` work across
   compartments. An intrinsic of the (mutable) program with no
   counterpart is refused rather than wrapped.
4. Everything else crosses as a **transparent** cross-compartment
   wrapper, so libraries work normally (`Array.isArray`, `Map` methods,
   `JSON.stringify` on wrapped values). *Deviation:* the design named a
   `SecurityWrapper<CrossCompartmentWrapper>` subclass; SpiderMonkey's
   `SecurityWrapper` answers `Array.isArray` with false and refuses
   built-in methods on wrapped objects (`Map.prototype.get`), which breaks
   ordinary libraries. The protection it would add (no writes to the
   other side's prototypes) is given by rule 3 instead, which also holds
   for built-in mutators such as `Object.defineProperty` called with the
   program's own objects.

A closure the program writes (`(p) => fs.readFileSync(p)`) is ordinary
code and crosses like any function: passing it is the program's decision
to delegate. `console.log` of a package's object prints the object
(`runtime/Inspect.cpp` looks through the wrapper without running code).

**Facades.** An ES module graph cannot span compartments, so **every**
import of another package goes through a facade module, even between two
pure packages (one rule, one behaviour). The facade is generated in C++
from the target's export names (read from its namespace's keys, which runs
no code; every name is written as an escaped string literal, never copied
from the package's source) and compiled in the importer's compartment:

```js
await import.meta.load();
const n = import.meta.namespace;
const e0 = n["default"];
export { e0 as "default" };
```

`import.meta.load` is a Forge function only the facade's own code can
reach. It evaluates the target in its compartment (once; every facade of
the same module shares that evaluation) and returns a promise of the
importer's realm that settles with it. The namespace is handed over as
`import.meta.namespace`, not as the promise's value, so a package that
exports `then` is not treated as a thenable. Because the facade awaits, a
program with dependencies always evaluates asynchronously; the target
still runs before the importer and in import order. JSON modules of
another package are reached the same way.

- **Deviation:** an importer sees the target's exports as they were when
  the target finished evaluating; a later reassignment of an `export let`
  is not visible to another package (tested).
- **Import cycles between packages** are a load-time error naming the
  packages (`cycle-a -> cycle-b -> cycle-a`). Cycles inside one package
  work as usual.
- A failure inside a package (a missing file, a syntax error, a refused
  import, a top-level `throw`) reaches the importer as the package's own
  error, wrapped.

**Code generation.** `eval`, indirect `eval` and `new Function` throw in
every dependency compartment (`Error`, code `PermissionDenied`); Forge
throws its own error because the engine's would mention a "CSP".
WebAssembly compilation follows `--disallow-wasm` as in the program.

**Known limits.**

- A package that patches built-ins or globals (a polyfill) cannot affect
  any other package or the program, and setting a global throws. A
  polyfill must be part of the program.
- Pure packages share one realm (RegExp statics, see R19 above).
- An intrinsic the walk does not find (an engine-internal one that script
  can still obtain) would cross as an ordinary wrapper. None is known; the
  hidden-intrinsic list is checked by the isolation test.
- Cold start: the walk records about two thousand objects per
  compartment. It runs only for programs whose `forge.json` lists
  dependencies (and for `--frozen-intrinsics`). To benchmark (D21).

## 6. Per-package permissions (step 9.4)

- A dependency declares `"permissions": { "read": ["./data"], "env":
  ["HOME"] }` in its `forge.json`; paths are relative to the **app**, the
  only place a person decides what a program may touch.
- The app grants them in its own `forge.json`:
  `"grants": { "b": { "read": ["./data"] } }`. Phase 14 moves approvals
  into `forge.lock` with version binding (R16).
- The effective policy is declared ∩ granted ∩ command line (D26). A
  dependency with no effective permission goes into the pure compartment.
- Each compartment's realm private points at its immutable policy; every
  native reads the policy from its own realm (D24); async jobs store it.
- Audit records gain a `package` field.
- Refusal messages name the package and say which of the three layers
  refused: not declared, not granted, or not allowed on the command line.

## 7. Proof (with each step)

- 9.1: runtime tests for relative imports, JSON modules, top-level await,
  dynamic `import()`, `import.meta`, refused specifiers, escaping the
  module root through `..`, a junction and a short name, importing a
  protected file; unit tests for the specifier code; the fuzzer covers
  `import.meta.resolve`; a realistic cold-start benchmark (D21).
- 9.3 (`tests/isolation`, `tests/frozen-intrinsics.js`): prototype
  pollution from a package, directly and through a program object's
  prototype; `then` on a frozen `Promise.prototype`; a pure package
  reaching Forge's natives; Forge's functions, objects, bound functions,
  `import.meta.resolve` and the global object refused at the boundary;
  the `Function` constructor reached through `obj.constructor.constructor`;
  `eval` and `new Function`; the override mistake; RegExp statics; timers
  and microtasks across compartments; snapshot semantics; a throwing
  package; a cross-package cycle; replays of the LavaMoat/SES escapes
  above (a spread `import()`, the app's top-level lexical bindings, a new
  realm).
- 9.4: confused deputy (a package passing its `fs` function to another);
  Wasm imports across compartments; per-package policies.
